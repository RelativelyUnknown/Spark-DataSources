# Spark-DataSources

Custom PySpark Python Data Sources. First experiment: **can a Rust (maturin/PyO3) extension back a
PySpark data source, and is it worth it vs pure Python or a CPython-native (Cython) extension?**

Short answer: yes, it works with no Spark-side changes. A `DataSourceReader.read()` is plain Python running
in the worker, so it can call any importable extension. Rust pays off mostly when it **returns Arrow
`RecordBatch`es** (zero-copy into pyarrow) and releases the GIL during I/O + parsing; returning row tuples
removes most of the gain.

## Quick start
```bash
make setup      # uv venv + uv sync (builds the Rust and Cython extensions; needs cargo + uv)
make test       # all implementations return identical DataFrames
make bench      # CLI benchmark
make notebook   # marimo notebook with sliders + chart
```
Requirements: Python 3.10+, Java 17+, Rust toolchain, `uv`.

## Data source
`spark.read.format("http_rust_arrow").option("url", base).option("total_rows", N).option("partitions", P).option("page_size", S).load()`
reads `GET {url}/records?offset=&limit=` pages (`id long, value double, name string, ts long`), one Spark
partition per row range. Formats: `http_py`, `http_py_arrow`, `http_rust`, `http_rust_arrow`, `http_cython`.
Call `spark_datasources.register_all(spark)` first.

## Results (1M rows, 4 partitions, local[4], 4-core sandbox, median of 3, single run — noisy)
Micro (one 50k-row page fetch+parse outside Spark):

| Implementation | rows/s |
|---|---|
| Python json → tuples | 1.03M |
| Python json → Arrow | 0.96M |
| Cython + orjson → tuples | 1.34M |
| Rust → tuples | 2.65M |
| Rust → Arrow | 4.62M |

End-to-end through Spark:

| Implementation | scan (read+sum) s | toPandas s |
|---|---|---|
| Python tuples | 0.81 | 1.72 |
| Python → Arrow | 0.53 | 0.93 |
| Rust tuples | 0.61 | 0.90 |
| Rust Arrow | **0.27** | 0.86 |
| Cython + orjson | 0.62 | 1.09 |

Takeaways: (1) Arrow output matters as much as the language — even pure Python gains ~1.5x from it;
(2) Rust+Arrow is ~3x faster than the baseline on scan, but once rows must travel to the driver
(`toPandas`) Spark's own JVM↔Python transfer dominates and the gap shrinks; (3) Cython+orjson gets part
of the way with far less build complexity; (4) the mock server and Spark JVM share the same 4 cores, so
treat numbers as directional.

## More workloads (same 4-core sandbox, single run, directional)
Animated chart of every table: open [`docs/results.html`](docs/results.html) (`make bench && make plot` regenerates).

| Workload | Python tuples | Python Arrow | Rust tuples | Rust Arrow | Cython |
|---|---|---|---|---|---|
| Gzip access logs, 1M lines (rows/s) | 1.07M | 1.34M | 1.33M | **2.26M** | 0.98M |
| NDJSON writer, 500k rows (rows/s) | 0.49M (Rows) | 0.68M | – | **2.69M** | 0.76M (Rows) |
| MQTT stream, 300k rows (rows/s) | 64k | – | 54k | – | 51k |

- **Logs:** regex parsing is already C-fast in Python, so Rust's win is mostly Arrow output + GIL-free decompression (~2x).
- **Writer:** biggest gap (~5x): Arrow batch in, `arrow-json` writes it with no per-row Python objects.
- **MQTT:** broker-bound (pure-Python `amqtt`); decode language does not matter. `SimpleDataSourceStreamReader`
  can only return rows, so there are no Arrow arms; replay after restart is not supported (PoC).

## Parquet: Rust reader vs Spark's built-in
`spark.read.format("parquet_rust").option("path", dir).load()` (also `parquet_pyarrow`, a pyarrow reference engine).
Implementation: arrow-rs `parquet` crate in `rust_ext` (footer inspection + a GIL-free streaming batch iterator),
planning/options in `src/spark_datasources/parquet_source.py`. Options mirror Spark's defaults:
`mergeSchema=false`, `pathGlobFilter`, `recursiveFileLookup=false`, `ignoreCorruptFiles=false`,
`ignoreMissingFiles=false`, `maxPartitionBytes=128MB`, `openCostInBytes=4MB`; files starting with `_`/`.` are
skipped, INT96/any timestamp reads as `timestamp[us, UTC]`, everything is nullable, columns match by name
case-insensitively with NULL for absent ones, and splits follow Spark's `FilePartition` packing.
Tests (`tests/test_parquet.py`) compare every result row-for-row with `spark.read.parquet` on a Spark-written
dataset (INT96 timestamps, decimal, date, array, struct, nulls, many row groups).

**Not supported:** hive-style partition discovery (`k=v` dirs), datetime rebase modes, filter pushdown,
`modifiedBefore/After`, and *automatic* column pruning — a Python data source only sees the schema you pass, so
use `.schema("d double")` to prune.

Results (10M rows, 8 Spark-written files, 315MB, snappy, local[4], single run, directional):

| Query | Spark built-in | Rust source | pyarrow source |
|---|---|---|---|
| full scan, all 8 columns | **1.13 s** | 1.58 s | 1.96 s |
| one column (`sum(d)`) | **0.29 s** | 0.41 s | 0.49 s |
| `count(*)` | **0.19 s** | 0.45 s | 0.51 s |
| decode one file outside Spark (rows/s) | – | 13.4M | 15.3M |

- The built-in reader wins every query: it is JVM-native, vectorized, prunes from the query and never crosses a
  process boundary. A Python data source pays Arrow transfer to the JVM (a ~0.4 s floor here even for `count(*)`).
- Rust is ~1.4x slower than built-in on a full scan, and ~1.2x faster than pyarrow inside Spark even though pyarrow
  decodes a single file a bit faster standalone (its decode threads compete with Spark's task threads; Rust
  releases the GIL and stays single-threaded per task).
- Tuning that mattered: asking arrow-rs to decode INT96 straight to `timestamp[us]` (schema hint) cut that
  column from 44 ms to 16 ms; reading the file into memory first was slower and was reverted.
- Takeaway: use a custom parquet source only for something the built-in cannot do (custom footer metadata,
  special layouts, side effects); for plain parquet the built-in reader is the faster choice.

### Why the Rust reader does not hand-roll unsafe byte-level decoding (measured)
Spark's vectorized reader and Polars' `polars-parquet` use hand-written decoders (raw byte arrays / `unsafe`,
per-bit-width unrolled bit-unpacking for RLE/bit-packed dictionary indices and levels, pages decoded straight into
Arrow-style buffers). Our reader delegates to arrow-rs' decoders, which already specialise bit-unpacking per width.
Before writing custom kernels I measured whether decoding is the bottleneck:

1. `bench/parquet_profile` (standalone Rust profiler, one 1.25M-row file, 8 columns): **86 ms** total =
   **58 ms (68%) page read + snappy decompression** and **28 ms (32%) decode + Arrow build**. PLAIN columns
   (`id`, `d`, `dec`) decode in 1-2 ms (a memcpy; nothing for `unsafe` to win). The slow spots are strings
   (8.5 ms, dictionary gather) and booleans (6.7 ms), then dictionary ints/dates (2-4 ms).
2. `bench/parquet_floor.py` (same Rust source, but batches decoded once and replayed from memory, i.e. a decode
   cost of zero): full scan = **1.47 s**, against **1.71 s** with real decoding and **1.14 s** for the built-in reader.

So decode (including snappy) is only ~0.24 s of ~1.7 s, and the decode+build part that custom kernels could speed
up is a few percent. The ~1.5 s floor is the Python data source path itself (Python worker, Arrow IPC to the JVM,
JVM-side conversion), which no decoder change can remove. Hand-written unsafe kernels would be justified for
standalone/Python-side use (where decode dominates), not for a Spark data source.

## Where Rust actually beats Spark/Python: concurrency and native libraries
Spark's built-in readers are hard to beat for formats the JVM already handles (see parquet above). Rust pays off
where a Python data source would otherwise be limited by the GIL, by one-thread-per-task, or by a missing library.

**Concurrent fan-out** (`fanout_*`, `tests/test_fanout.py`): each Spark partition fetches 100 small pages from an
asyncio mock server (own process, injected latency). All arms return Arrow, so only the I/O strategy differs.
Spark end-to-end, 400k rows, 4 partitions, 20 ms latency, 64 in flight:

| Strategy | time | rows/s |
|---|---|---|
| Python sequential | 2.51 s | 160k |
| Rust sequential | 2.34 s | 171k |
| Python threads | 0.65 s | 617k |
| Rust threads | **0.29 s** | 1.37M |
| Rust async (tokio) | 0.32 s | 1.27M |

- Latency-bound sequential code gains nothing from Rust (2.5 s vs 2.3 s); the win appears only with concurrency.
- Python threads plateau at ~300-450 pages/s however many requests are in flight: JSON parsing and Arrow
  building hold the GIL. Rust does fetch + parse + Arrow build with the GIL released and keeps scaling
  (up to ~2.5k pages/s outside Spark, 20 ms latency, 512 in flight), i.e. ~2.2x Python threads in Spark and
  ~5-6x outside it.
- tokio did **not** beat plain OS threads here (0.32 vs 0.29 s). Async should matter at thousands of open
  connections, which this setup does not reach; the benefit is the GIL-free pipeline, not the runtime.
- Caveat: the mock server tops out near 4.1k req/s (reported in the probe), so Rust's high-concurrency numbers are
  partly server-bound; they are a lower bound.

**Native-library enrichment** (`enrich_*`, `tests/test_enrich.py`): H3 cell index + xxh3-64 hash + Unicode word
count over generated points. The Rust arm uses `h3o`, `xxhash-rust`, `unicode-segmentation` and is asserted
**bit-identical** to the Python arm (`h3` and `xxhash`, which are themselves C extensions, plus `re`).
Spark has no built-in H3 or xxh3.

| Arm | kernel, 50k rows (rows/s) | Spark, 2M rows (rows/s) |
|---|---|---|
| Python loop, tuples | 364k | 747k |
| Python loop, Arrow | 390k | 1.00M |
| Rust, Arrow | **867k** | **1.81M** |

- ~2.2x on the kernel and ~1.8x in Spark against the best Python arm. The Python arm is not naive: it calls C
  libraries, so what Rust removes is the per-row interpreter loop and boxing, not the library itself.

## Notes / caveats
- The MQTT stream benchmark can stall when run as the 4th section of a long `run_bench.py` session (the pytest
  MQTT tests pass); use `--only <section...>` to run sections separately — results merge into `--json`.
- Native modules are **not pickled** to executors: they must be installed on every worker
  (`abi3` wheel from maturin makes that one wheel per platform, not per Python version).
- Workers must use the same interpreter: tests/bench set `PYSPARK_PYTHON=sys.executable`.
- Not covered yet: filter pushdown, cluster-mode, free-threaded Python, >4k-request/s servers for the fan-out test.
